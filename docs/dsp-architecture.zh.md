# DSP 架构说明

本文件由根目录 `introduction.md` 移入 `docs/`，作为现有 DSP 架构背景资料保留。

### 引言  
在数字广告生态系统中，DSP通过实时竞价广告库存发挥着关键作用。本文将介绍构建该DSP的架构和技术考量。  

### 系统需求  
主要技术目标包括：  

- **高吞吐量**：每天处理30亿次来自多个广告交易平台的OpenRTB v2.5竞价请求（峰值达每秒40,000次）。  
- **低延迟**：在100毫秒内返回优化后的广告。  
- **频次控制**：实现服务器端对用户的展示次数限制。  
- **动态供应端处理**：与供应方平台（SSP）不同，DSP无法预先获取发布商信息，需实时区分流量来源以优化竞价。  

### 基础设施设计  
为满足这些需求，系统架构如下：  

1. **广告服务器（3台）**：  
   - 负载均衡，分发竞价请求。  
   - 支持水平扩展，可增加服务器应对更高流量。  

2. **Redis缓存服务**：  
   - 集中存储实时频次控制数据。  
   - 支持每秒100,000+次读写，满足40,000 RPS的目标。  

3. **MySQL数据库**：  
   - 持久化存储活动元数据、受众定向规则和账务数据等。  

4. **日志聚合与分析服务器**：  
   - 收集并处理竞价、获胜和点击日志，用于报告和优化。  

为应对更高流量，可通过用户ID将请求负载均衡到不同子集群。  

### 活动与受众定向  
#### 1. 用户界面  
平台支持广告主认证和管理活动，通过多标签定向定义受众。该组件采用标准的Web应用架构，基于数据库操作。为加速开发，我们复用了之前供应方平台（SSP）的UI层，该平台基于Go语言的Molecule框架实现。  

广告主可使用符合OpenRTB v2.5标准的定向标签：  
- **地理定向**：国家、城市、ISP、连接速度。  
- **人口统计**：年龄、性别、语言。  
- **设备定向**：制造商、操作系统、浏览器。  
- **时间定向**：星期几、小时。  
- **内容分类**：品牌安全的白名单/黑名单。  

目前无需在协议之外扩展更多受众标签，但未来可支持。  

#### 2. 频次控制  
广告频次控制限制同一用户在指定时间范围内的广告展示次数，避免广告疲劳，并通过合理展示频率优化广告支出。  

系统支持：  
- **展示上限**：用户在时间窗口内的最大展示次数。  
- **展示间隔**：两次连续展示的最小时间间隔。  
- **点击上限**：点击次数限制（因其价值较高，优先级更高）。  

数据结构如下：  
```go
// 活动定向配置
type Cap struct {
    CapNumber    uint8  // 允许的最大展示次数
    CapPeriod    uint16 // 时间窗口（分钟）
    CapThrottle  uint16 // 最小展示间隔（分钟）
    ClickNumber  uint8  // 允许的最大点击次数
    ClickPeriod  uint16 // 点击统计窗口（分钟）
}

// Redis动态记录
type Fcap struct {
    Total     uint8  // 总展示/点击次数
    StartYM   uint8  // 开始时间戳（年-月）
    StartDHM  uint16 // 开始时间戳（日-时-分）
    Last      uint16 // 距离最后一次展示的分钟数
}
type BothCap struct {
    Imp Fcap // 展示统计
    Cli Fcap // 点击统计
}
```  
其中：  
- `CapNumber`表示在`CapPeriod`（分钟）内允许的展示次数。  
- `CapThrottle`表示两次连续展示的最小间隔。  
- `Fcap`中的`Total`记录从开始时间（`StartYM`, `StartDHM`）起对用户的总展示次数；`Last`记录距离最后一次展示的分钟数。  

频次控制数据通过Redis读写。  

#### 3. 缓存更新  
广告主频繁修改活动和受众标签，变更会保存到数据库。但由于实时广告投放中直接访问数据库速度过慢，我们实现了活动和受众数据的缓存版本。  

早期在Rubicon Project（现Magnite）工作时，我们曾开发高性能广告服务器，采用文本文件缓存，刷新周期约30分钟，勉强满足业务需求。  

当前方案中，我们引入了NATS发布-订阅消息系统。该技术通过消息广播实现缓存数据在集群节点间高效同步，构建分布式缓存数据库，每10分钟更新一次，性能较之前提升3倍。  

NATS消息系统还作为传输层，将竞价请求、响应、获胜通知和点击等日志传递至中央聚合器。这些数据经处理后生成全面的流量分析，支持财务对账（账务）和实时活动优化。  

### 系统工作流  
系统架构包含五个核心组件，作为独立服务运行：  

1. **unify**  
   - **部署**：作为systemd服务运行在3个节点。  
   - **功能**：80端口的HTTPS服务，处理：  
     - 广告交易平台的竞价请求  
     - 广告主活动配置  
   - **性能**：优化低延迟响应。  

2. **spread**  
   - **部署**：作为systemd服务分布在3个节点。  
   - **功能**：缓存同步服务，负责：  
     - 接收更新的缓存数据  
     - 将缓存写入本地磁盘  
   - **可靠性**：确保节点间数据一致性。  

3. **nats-client**  
   - **部署**：聚合器节点上的systemd服务。  
   - **功能**：日志收集服务，负责：  
     - 订阅流量日志流  
     - 将结构化日志写入持久存储  
   - **吞吐量**：支持高容量日志处理。  

4. **redis-cache**  
   - **部署**：聚合器上每10分钟运行的定时任务。  
   - **功能**：缓存发布服务，负责：  
     - 打包更新的缓存数据  
     - 发布到NATS消息总线  
   - **一致性**：维护集群缓存一致性。  

5. **ledger**  
   - **部署**：聚合器上每10分钟运行的定时任务。  
   - **功能**：数据聚合服务，负责：  
     - 处理并汇总日志数据  
     - 将分析结果保存到数据库  
   - **报告**：生成财务和性能指标。  

### 未来优化  
- **机器学习**：实时竞价价格优化。  
- **边缘缓存**：降低全球流量的延迟。  

该架构结合现代分布式系统原则与精选组件（Redis、NATS、Go），满足了程序化广告的严苛要求。
