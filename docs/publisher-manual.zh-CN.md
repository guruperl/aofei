# 流量方（发布商）接入手册

本手册面向通过 W8M 管理网站、App 和广告位，并使用网页广告码或 `POST /pz` 接口接入广告服务的流量方（发布商）。内容包括账户与流量资源、网页和 SDK/API 接入、响应处理、计量报表和常见问题。平台域名、账户启用、商务结算和生产支持渠道由运营方提供。

当前平台已经实现 Web 广告码、App/服务端 `/pz` JSON/OpenRTB 协议示例、服务端
底价、供应分类、卖方透明度、分账户报表和人工结算。强化登录与权限、流量质量
审查、托管收款和真实外部需求方流量都由运营方分别启用。Android/iOS 原生 SDK
仍为需求驱动的计划项；仓库目前没有可发布、可升级承诺的原生 SDK 包，不能把
协议示例称为官方移动 SDK。各功能的实现与启用状态见
[文档与里程碑索引](README.md)。

## 1. 账户和流量资源层级

流量方的流量资源按以下层级管理：

```text
流量方账户（发布商）
└── 流量源（网站或 App）
    └── 广告位
```

登录后的页面位于：

```text
https://<平台域名>/goto/pub/g/...
```

仪表盘可查看主要广告位、主要广告活动和近 24 小时数据。报表由后台日志与账务任务定时汇总，并非请求级实时数据。

账户资料中的“卖方透明度”用于说明由谁销售这批广告资源，包括卖方 ID、
卖方类型、广告系统域名（ASI）、公开名称和域名。流量方提交或修改后，须由
平台运营方复核授权；已授权内容一旦改变会自动恢复为“待审核”。这些公开资料
用于 OpenRTB 供应链和报表分类，不会改变当前流量方账户的收入归属、结算主体
或收款方式。

### 账户安全与双重验证

平台启用账户安全功能后，登录除了密码，还需要身份验证器生成的六位验证码；在
身份验证器暂时不可用时，可以输入一枚尚未使用的恢复代码。首次登录会先进入
“账户安全”页面。请把一次性设置密钥或标准 TOTP 地址加入身份验证器，输入当前
验证码确认，并立即把生成的恢复代码保存到离线安全位置。完成前，系统不会开放
流量源、广告位和报表页面。

密码至少需要 12 个字符。修改或找回密码、停用双重验证、或由运营人员重置双重
验证后，所有现有会话都会撤销。请使用页面里的退出按钮结束当前会话，不要仅
关闭浏览器。账户安全页可以用当前验证码更新恢复代码；新代码生成后，旧代码
立即失效。

“忘记密码”链接只发送到流量方账户登记邮箱，并在短时间内失效。已启用双重
验证的账户还必须提交一枚恢复代码，系统才会在一个事务中更新密码、消费该代码
并撤销会话。邮箱、身份验证器和恢复代码均不可用时，请联系运营人员完成线下
身份核验和有原因记录的重置；客服不会要求你发送设置密钥、当前验证码或恢复
代码。流量方只能维护自己名下的流量资源；卖方授权、其他账户资源和平台路由
始终由服务端权限控制。

注册或申请找回密码时，页面可能在提交前显示 Cloudflare 人机验证。这项验证用于
限制批量注册和垃圾邮件，不会要求输入流量方账户密码，也不会改变邮箱验证流程。
验证失效时请刷新页面后重新提交；出现“提交过于频繁”时请稍后再试，不要连续
点击。持续无法提交可联系 `support@w8m.com`。

## 2. 创建流量源

进入“流量源/站点”后选择新增，并检查：

- 流量源名称；
- 类型：`Web` 或 `App`；
- Bundle/Domain：网站填写域名，Android App 填包名，iOS App 填商店数字 ID；
- 介绍网址；
- 流量环境：网站、App、联网电视（CTV）、数字户外（DOOH）或其他；
- 规范标识：网站填写审核域名，App 填写包名或应用标识；
- 公开审核地址：只填写公开的 `http` 或 `https` 页面，不得包含账号密码；
- 接入方式：ADX、网页广告码、SDK 或服务端 API；
- 流量范围（白名单/黑名单）及启用状态。

这些字段采用固定选项，便于审核和报表保持一致。现有直连接入中，`Web` 应与
“网站 + 网页广告码”一致，`App` 应与“App + SDK”一致；不要用接入方式代替
启用审批或来源校验。

Web 直连接入有严格的来源校验。生产页面实际发送的 `Origin` 或 `Referer` 主机名必须与平台缓存中的站点主机名完全一致。不同子域名不会自动视为相同站点，协议、端口和部署代理也应在上线前由运营方一起核对。

修改流量源后，如果生成的接入代码仍被拒绝或仍使用旧数据，请联系运营方刷新静态缓存；`/pz` 请求链路不会直接查询 MySQL。

## 3. 创建广告位

在一个流量源下选择“添加广告位”，配置：

- 广告位名称；
- 宽度和高度；
- 最低竞价（USD CPM）；
- 所用语言、设备平台和页面位置；
- 可接受的 MIME、素材特点和展开方式；
- 流量质量条件、广告活动质量要求和行业匹配；
- 媒体形式意向：横幅、视频、原生、音频或多形式；
- 展示位置与渲染场景：首屏、信息流、插屏、激励、悬浮等受控选项；
- 刷新方式：不刷新、定时刷新或事件触发；定时刷新须填写 15 至 3600 秒；
- 广告密度、流量审核状态、资源来源和管理责任方；
- 启用状态。

广告位保存的尺寸是运行时可信尺寸。浏览器或 SDK 请求中自报的宽高只是请求元数据，不能覆盖平台配置；请求令牌携带的尺寸与缓存配置不一致时会返回 `400`。

最低竞价是平台在该广告位采用的服务端底价，单位为 USD CPM。请求可以
提出更高底价，但不能降低这里配置的值；实际竞价采用两者中的较高值。

如果修改尺寸，应重新从广告位页面取得接入代码，不要沿用旧 `slot` 令牌。

## 4. 获取并部署网页广告码

广告位列表按流量源类型提供接入样例：`Web` 流量源只显示网页广告码，
`App` 流量源只显示 SDK/API 接入代码，避免把两种身份和来源规则混用。
对应行可以提供：

- “广告码”：查看网页接入样例；
- “复制”：复制完整 HTML；
- “下载”：下载名为 `aofei-slot-<slot_id>.html` 的样例文件；
- “API码”：查看 SDK/API 请求样例。

推荐直接使用页面生成的样例，因为其中的 `site` 和 `slot` 是平台生成的打包标识。不要自行猜测、截断或交换这些值。

网页样例的基本形状如下，生产代码应使用广告位页面给出的实际值：

```html
<script src="https://<广告服务域名>/js/ads.js"></script>
<div id="pz-slot-13" style="width:300px;height:250px"></div>
<script>
pzLoadAds({
  "platform": "browser",
  "site": "<页面生成的 site 令牌>",
  "adUnits": [{
    "code": "pz-slot-13",
    "slot": "<页面生成的 slot 令牌>",
    "mediaTypes": {"banner": {"size": [300, 250]}}
  }]
});
</script>
```

`ads.js` 默认根据自身脚本 URL 推导 `/pz` 地址。如果静态文件和广告服务不在同一地址，可以显式指定：

```js
pzLoadAds(payload, { endpoint: "https://<广告服务域名>/pz" });
```

部署时注意：

- `adUnits[].code` 是页面 DOM 元素 ID 和响应顺序标识，不是流量资源身份；
- 同一个请求内，非空 `code` 必须唯一；
- `site` 标识流量方账户和流量源，`slot` 标识广告位及尺寸；
- 支持的媒体类型为 `banner`、`video` 和 `native`；
- 浏览器请求必须带有有效 `Origin` 或 `Referer`，且所有出现的来源主机都必须与缓存站点完全一致；
- `Origin: null`、来源缺失、URL 非法、主机不一致或仅子域相近都会被拒绝；
- `/pz` 的跨域访问不携带凭据，不能依赖跨站 Cookie 一定可用。

当前 `ads.js` 不会把返回素材直接写入宿主页面。填充素材进入不带
`allow-same-origin` 的独立 `srcdoc` 沙箱 iframe；容器会标记 `filled`、
`no-fill` 或 `error` 状态，无填充时会清空内容。流量方仍应采用平台生成
的代码，不要移除沙箱或把返回字符串改成宿主页的 `innerHTML`。

默认或 `responseFormat:"html"` 的成功响应为按输入顺序排列的 HTML 字符串数组。未填充位置用空字符串表示：

```json
["<iframe ...></iframe><img ...>", ""]
```

有效请求即使全部无填充也返回 `200`。前端应把空字符串当作正常无广告，隐藏或回收对应容器，不要当成网络错误反复快速重试。

## 5. SDK 与服务端 API 接入

SDK 请求仍发送到：

```text
POST https://<广告服务域名>/pz
Content-Type: application/json
```

P03 的 App 请求签名功能已实现但默认关闭；在完成剩余 P03 灰度门槛之前，页面
样例仍是未签名的兼容样例，不能把它称为已认证生产接入。平台通知启用后，流量方
须在完成 S02 登录、具名权限和近期 MFA 后，通过“请求凭证”页面为一个已审核
App 签发凭证。私密值只显示一次，应存入服务端或受控密钥管理系统，绝不能写入
公开示例或移动端源码。

启用认证后，每次请求必须以新的随机数和当前 Unix 秒，对精确的解压后 JSON
正文及规范 `POST /pz` 上下文生成 Ed25519 签名，并发送
`X-W8M-PZ-Credential`、`X-W8M-PZ-Timestamp`、`X-W8M-PZ-Nonce` 和
`X-W8M-PZ-Signature`。凭证只适用于其绑定的流量方和 App；缺失、过期、重放、
正文变化、跨 App 或已撤销证明都会在竞价前失败。具体规范见
[直接 SSP 请求真实性契约](direct-ssp-authenticity.md)。

建议使用广告位页面“API码”中的实际令牌。请求示例：

```json
{
  "platform": "sdk",
  "responseFormat": "json",
  "site": "<页面生成的 site 令牌>",
  "app": {"bundle": "example.com"},
  "device": {"os": "Android", "language": "zh"},
  "adUnits": [{
    "code": "pz-slot-13",
    "slot": "<页面生成的 slot 令牌>",
    "mediaTypes": {"banner": {"size": [300, 250]}}
  }]
}
```

SDK 请求不读取、设置或传递 `aofei_pz_uid` Cookie。可以提供 OpenRTB 风格的 `app`、`device`、`user` 和 `regs` 对象：

- 只有 P03 Publisher/App 请求签名有效，并且平台隐私决策独立确认允许个性化时，`device.ifa`、设备 ID、`user.id` 与 `buyeruid` 才会进入本地匹配；未认证的 SDK 兼容请求即使提交形式有效的同意字符串也会降为上下文模式；
- 上下文或受限模式会在匹配前删除这些标识、IP、原始 User-Agent、精确位置和人口属性；
- HTTP 头可用于请求处理和语言等上下文派生，但不能作为上下文身份后备；
- `app.id`、`app.bundle` 或 `app.domain` 如果提供，必须为空或与平台验证出的流量源身份完全一致。

流量方必须从已经审核的 CMP/隐私流程传递适用的 GDPR/TCF、GPP/US Privacy、COPPA、GPC/DNT/LMT 等信号；不得伪造同意字符串，也不能因示例中省略信号就默认获得个性化授权。没有明确信号时平台仍可做上下文投放。

SDK 可省略 `Origin` 和 `Referer`；但只要提供其中之一，仍必须通过完全一致的主机校验。

### 响应格式

| `responseFormat` | 响应 |
|---|---|
| 省略或 `html` | 每个广告位对应一个 HTML 字符串。 |
| `json` | 每个广告位对应一个结构化的填充/未填充对象。 |
| `openrtb` | 一个 OpenRTB `BidResponse`；全部无填充时 `seatbid` 为空。 |

结构化 `json` 填充对象可能包含 `filled`、`adm`、展示与点击地址、价格、币种、广告主/广告活动/广告素材 ID 以及宽高。原生广告还可包含解析后的 `native` 对象。外部需求方竞价返回的填充会保留其 `adm`、价格、ID 和尺寸，但不一定包含仅适用于本地广告素材的独立 `impressionUrl` 与 `clickUrl`。

客户端负责按广告类型安全展示 `adm`，并在使用结构化响应时按协议触发展示或点击测量。不要修改平台生成的签名参数。

## 6. 浏览器身份、隐私与代理

浏览器接入只有在当前请求通过已配置的个性化授权后，才可使用 `aofei_pz_uid` 作为尽力而为的假名身份：

- 空 `platform` 或 `platform:"browser"` 在授权成立时可以读取已有有效 Cookie，或设置供后续请求使用的 Cookie；
- 新创建的 Cookie 只会在浏览器以后回传时成为用户身份；
- 缺失、拒绝、退出、无效、COPPA 或尚未映射的 GPP 信号不会读取或设置 Cookie；
- Cookie 因跨域策略缺失时不阻止上下文投放，系统不会用 IP 与 User-Agent 拼接身份；
- SDK 流量完全不使用该 Cookie。

如果流量经过 CDN 或反向代理，代理出口必须先由运营方加入受信列表，平台才会采用 `X-Forwarded-For` 或 `X-Real-IP` 中的客户端地址。流量方不应自行伪造这些请求头，应与运营方共同验证代理链路。

## 7. 填充、测量与报表

通过 `/pz` 投放的本地素材复用 DSP 的签名展示和点击测量。账务中的展示与结算金额以有效展示跟踪到达为基础，点击以有效点击跟踪到达为基础。竞价价格使用 USD CPM（千次展示价格）；一个有效展示对应的账务金额按 `CPM / 1000` 计算，例如 CPM 为 `2.5` 时计入 USD `0.0025`。

在平台启用外部需求方竞价功能时：

- 本地无填充可使用 `Fallback` 路由；
- 只有独立的 Always 开关也启用时，外部竞价才可与已有本地广告竞争；
- 外部回调代理准备失败时，如已有本地赢家则保留本地赢家，否则该广告位保持无填充。

这些选择对流量方接入协议透明，不需要更改 `ads.js` 或请求结构。

“市场分析”按当前登录流量方强制隔离，可按流量源、网站/App、广告位、
流量环境、接入方式、媒体形式、展示位置、刷新方式、质量分类、已授权卖方、
国家/地区和设备查看展示、点击、CTR、收入和有效 CPM。未填写或历史数据会
明确显示为 `Unknown`，未经授权的卖方不会被归入某个卖方 ID。时间统一使用 UTC，
金额为六位小数 USD。该页面不会显示广告主花费、平台成本/毛利、竞价方凭据
或其他流量方资料。页面标记为 `partial` 或 `unavailable` 时，表示日志、时间片
或依赖资料仍不完整，不能把它当作真实零收入；持续异常时请向运营方提供 UTC
时间范围、流量源 ID 和广告位 ID。

平台运营方可按 UTC 日、UTC 自然周（周一至周日）或 UTC 自然月生成流量方结算单。结算单从已完成的日账务汇总生成，保留六位小数，并经过草稿、暂停、确认、结算登记或更正流程。已确认记录的更正会保留原记录并建立替代结算单，不会回写展示事实。流量方如需结算单或 CSV，应提供账户 ID 和账期；不要通过工作台、邮件或工单提交完整银行卡号、银行账号或路由号码。

### 托管收款账户（由平台启用时）

如果运营方已启用“媒体收益结算账户”，流量方可从工作台进入 Stripe Connect
Express 托管页面，完成经营主体、身份和收款银行资料核验。W8M 仅保存不透明的
Connect 账户标识，不会在自己的页面采集或显示完整银行账号、路由号码、证件
图片或支付服务商密钥。

托管页面显示完成后，账户仍需经过服务商 `account.updated` 就绪确认和 W8M
独立人员复核，才可用于打款。服务商以后取消就绪资格时，W8M 会自动撤销该
绑定；恢复就绪后仍需重新复核。请勿重复建立多个收款账户来处理状态延迟，
应使用原绑定的“继续托管开通”入口。

平台只能针对 `Confirmed`（已确认）且未进入 `Held`（暂停）的结算单建立和
执行打款，活动打款申请合计不能超过结算单金额。工作台中的 `Submitted` 仅表示
已按原幂等请求提交，最终到账还取决于服务商转账、外部银行付款、退款/冲正和
对账状态。出现失败、争议或资料补充要求时，请提供 W8M 操作号和服务商不透明
标识；不要通过工单发送银行资料或证件。

平台启用“流量质量审查”后，流量方只能查看本账户的案件、规则版本、受控证据
摘要、处理结论和执行状态。来源/App 身份冲突、重复、异常事件顺序或异常比率
只有在命中已发布的具名规则并经过人工复核后，才可能进入灰度限制或账单暂停。
系统故障、超时、无填充、请求格式错误和外部竞价失败本身不是无效流量；证据
缺失或不完整时只观察，不执行拦截或账务变更。

对“无效流量”结论有异议时，可在案件页面提交具体申诉理由。请提供 UTC 时间、
流量源和广告位 ID 及业务背景，不要粘贴 Cookie、设备标识、竞价令牌、完整请求
正文或个人资料。申诉由独立管理员处理；原始展示、点击、报表和账务事实不会被
删除或静默改写。

## 8. 错误与排查

| 现象 | 常见原因 | 处理 |
|---|---|---|
| `400 Bad Request` | JSON 非法、令牌错误、广告位不存在、Web/App 类型不符、尺寸或底价非法、媒体类型不是唯一一项、`code` 缺失/非法/重复 | 使用广告位页面最新样例，逐项核对请求字段。 |
| `403 Forbidden` | 浏览器来源缺失或主机不完全匹配；SDK 提供了不匹配来源 | 核对生产页面主机、`Origin`、`Referer` 和缓存站点配置。 |
| `401 Unauthorized` | 启用 SDK 认证后，证明缺失、非法、过期、重放、正文或 App 范围不符 | 重新生成一次性随机数并签名精确正文；检查凭证范围、有效期和轮换状态。 |
| `503 Service Unavailable` | SDK 公钥快照过旧/不可用，或 Redis 重放依赖不可用 | 不要绕过认证；按退避策略重试并联系运营方检查 MySQL 快照刷新和 Redis。 |
| `413 Payload Too Large` | 请求体超过限制 | 减少单次请求广告位数量或无关字段。 |
| `200` 且空字符串/未填充 | 请求合法，但没有通过尺寸、底价、预算、定向或路由的广告 | 当作正常 no-fill；向运营方提供时间、站点、广告位和请求 ID 排查。 |
| 页面没有渲染 | DOM `code` 不一致、脚本加载失败、CSP/网络拦截、未处理空响应 | 检查浏览器控制台、网络请求和容器 ID。 |
| 修改后仍是旧行为 | MySQL 已更新但运行缓存未发布 | 联系运营方刷新缓存并确认生成时间。 |
| 报表延迟 | 日志轮转或账务时间片尚未完成 | 等待计划任务；持续缺失时提供时间范围和广告位 ID。 |

无效令牌和来源校验失败的请求不会进入竞价。排查 `400/403` 时，请先记录发生时间、页面地址、请求状态、`Origin`/`Referer`、流量源和广告位，再交由运营方检查访问日志；这类请求不会出现在投放或账务报表中。

## 9. 上线验收清单

- 流量源类型、Bundle/Domain、站点主机及状态正确；
- 流量环境、规范标识、接入方式及公开审核地址正确；
- 广告位尺寸、服务端最低竞价、媒体形式、展示位置、刷新和质量规则正确；
- 卖方资料已经平台运营方审核；如资料变更，确认授权状态已重新复核；
- Web 只使用网页广告码，App 只使用 SDK/API 样例；
- 使用页面新生成的 `site` 与 `slot` 令牌；
- 浏览器实际 `Origin`/`Referer` 与缓存站点完全一致；
- 每个非空 `code` 在请求内唯一，并有对应 DOM 容器；
- 测试了至少一次有填充和一次无填充响应；
- SDK 不依赖 Cookie，传递经审核的适用隐私信号，且只在有合法用途时提供设备或用户标识；
- 已与运营方确认缓存刷新、报表延迟和故障联系渠道。
